# 本地实操：开发 → QA → SRE

这次交付沿用上一轮的订单导出实现和 8 项测试。新示例增加了一个真实 HTTP 入口和一项跨页验收。首个候选在 HTTP 路径仍返回第一页，能稳定重现漏掉订单 `05` 的缺陷。上一次的工作目录、已签收产物和运行保持原样。

## 走一次真实流程

1. 依照[启动说明](../README.md)打开本机工作台，运行 `npm run example:release`。该命令在已配置工作根目录中复制一份独立样例，输出新的绝对路径。
2. 新建团队，选择「开发 → QA → SRE 测试发布」。为三个角色选择本机发现的 Paseo provider 与模型，把工作目录都设为刚创建的目录。核对候选清单、QA 测试命令、允许的自动修复次数、SRE 的测试环境名和团队自己的发布及验证命令，再保存流程。企业自己的测试和发布工具也可以按参数数组配置。
3. 发起委托。开发角色可先检查现有实现，再显式提交第一版实现产物。ohoo 封存所选文件，把出站产物修订与候选 SHA-256 绑定。后面修改工作区文件不会改变已提交版本。
4. QA 在独立的真实 Paseo 会话接单，使用终端工具调用本次任务专用的命令入口。在该候选的临时副本中运行团队测试。退出码非零时，失败回执随原产物退回开发；在获授权的返工次数内，开发 agent 修复后重新封存为同一产物的新修订并自动复验。测试流程保留旧失败结果。
5. QA 的测试退出码为零且真实回合结束后，系统签收本次候选，提交带摘要和命令回执的 QA 报告。SRE 在自己的会话中先执行团队配置的部署命令，再执行验证命令。二者必须属于同一候选、同一目标。验证完成且 SRE 回合结束后运行关闭。

## 订单团队如何配置发布

| 角色 | 本示例的已配置工具 | 用途 |
| --- | --- | --- |
| QA | `node --test orders.test.mjs acceptance.test.mjs` | 用原有 8 项回归及新增的 HTTP 验收检查候选 |
| SRE | `node team-release.mjs deploy` | 校验并持久化相同候选，启动或复用本机测试服务，记录目标、地址与部署结果 |
| SRE | `node team-release.mjs verify` | 从正在运行的服务请求 `/health`、`/orders.csv`，核对摘要、跨页结果、账号可见范围、排序及空结果 |

实际命令以程序和参数数组保存，服务端直接启动该程序。候选以排序后的「路径、内容 SHA-256」清单计算总摘要；一个候选最多 128 个常规文件，合计 16 MiB。每个动作从已封存候选建立独立工作副本。团队 CLI 可以通过 `OHOO_CANDIDATE_SHA256`、`OHOO_CANDIDATE_FILES`、`OHOO_OPERATION_ID`、`OHOO_RUN_ID`、`OHOO_TARGET` 与 `OHOO_RELEASE_STATE_DIR` 获得本次执行信息。测试环境的持久目录按团队和目标划分。

## 怎么核实结果

在「运行记录」查看 v1 的测试退出码和失败用例，再比较 v2 的通过回执、部署回执及验证回执中的候选摘要。模型回复供人阅读，状态转移依据持久化命令结果。缺少验证、命令失败或结果未知时，界面保留阻塞原因；部署动作使用固定操作号，重复调用只读取原动作。Paseo 如需本机工具授权，应核对本次角色、命令和目录后处理。

对于随仓库附带的订单测试服务，可用下列命令查询当前地址；不再需要服务时可显式停止。这会作用于该团队、该目标正在运行的示例服务，保留历史候选和回执。

```sh
npm run example:target -- status <运行ID>
npm run example:target -- cleanup <运行ID>
```
