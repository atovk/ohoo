# 本地实操：需求整理 → 开发设计 → 开发负责人评审

这个例子把两个本机 coding agent 放在不同的 Paseo 会话中。需求角色提交的是一份带版本的需求；开发角色接收后直接读取样例项目、起草方案。负责人在自己的账号下评审。每一步进入团队记录的内容都来自显式提交，原始私聊保留在所属角色会话中。

## 准备项目与团队

1. 启动 Paseo 和 ohoo，按[本地 MVP 说明](../README.md)以本机负责人身份进入。执行 `npm run example:design`，复制输出的工作目录。每次命令都会准备一份新的订单列表示例，其中有分页、账号权限、状态筛选及一个基线测试，适合让开发 agent 真正读代码和实施。
2. 在「成员」创建邀请，让另一个浏览器身份加入工作区。在新建团队时选「需求与研发设计评审」，将「需求整理」和「开发设计」绑定到本机执行账号，为它们选择能实际调用的 Paseo provider、模型和刚准备的目录。将真人「开发负责人」指派给受邀成员。
3. 核对开发角色已启用自动接手，负责人采用设计评审模式。前者授权接到明确产物或退回意见时启动该角色；后者授权这名负责人用指定版本的设计启动实施。旧团队默认沿用既有手动模式。发起一次工作，例如「为已支付订单增加全量导出」。

## 实际操作

| 阶段 | 在工作台中怎么做 | 应当看到的结果 |
| --- | --- | --- |
| 提交需求 | 在需求整理会话里要求起草需求。例：「导出当前账号有权查看的全部已支付订单，按列表顺序返回，不受页大小限制。」选定回复中的需求正文与字段，预览后明确提交 | 平台记录需求 v1 并为开发角色登记一次自动交接。即使不打开开发节点，它也会用自己的 Paseo 会话开始设计 |
| 开发设计 | 打开开发节点观察交接状态和真实回复，核对 agent 引用的代码与验证办法。选择要交付的设计正文及摘要，提交给负责人 | 下游输入有需求的 ID、版本和显式交付内容。开发草稿在明确提交前只留在本角色会话 |
| 负责人改稿 | 在「待我签收」打开当前设计，直接修改正文或字段并保存 | 得到新的待审修订。原稿可追溯，新版注明编辑人。改稿会固定新版本，尚未授权实施 |
| 退回修改 | 针对当前设计版本填写意见，例如「补充空结果以及跨页排序的回归测试」 | 任务回到开发设计。已授权自动接手的开发 agent 在原会话中收到退回的具体版本和意见，并生成修订草稿。开发重新显式提交 |
| 确认开工 | 核对待审版本和执行目录，再确认开工 | 本次运行记录批准人及设计版本，由原开发 agent 在同一会话中依据该版本开始实施。这里是真实的本机工具调用，工作目录使用刚准备的样例项目 |
| 收尾 | 开发核对实际变更和测试，提交实现结果。负责人按该版签收或退回补充 | 实现结果有独立产物 ID 和版本。终点签收后运行关闭，设计与批准历史仍可查 |

以服务端回执和实际文件/测试为依据。Paseo 等待权限时，由相应成员在原生会话核对并处理。派发后的未知结果沿原消息 ID 核对，平台不会把超时自动当作执行成功，也不会重新发送可能已经执行的开工指令。

两个独立的浏览器身份分别承担发起与评审。需求整理使用 Paseo 会话 `1dd3a75e-6110-5691-8f00-d41a36249ef1`。需求 v1 提交后，开发会话 `0fe6b83b-94b9-5452-8cb8-1e1bd141384d` 自动读取明确交付的需求及样例仓库，无需成员进入开发节点发指令。三次自动执行的实际输入均保留公开验收条件，均未包含需求角色的私有校验词。

负责人修改方案 v1 产生 v2，并针对 v2 退回意见。开发在原会话提交修订稿 v3，负责人批准的正是 v3。实施期间，对该示例目录内的写入请求给予了一次 Paseo 原生授权。开发实际实现 `exportOrderRows`，样例项目中 8 项测试通过，另以独立输入核验了跨页、账号隔离、排序与空结果。负责人签收单独的实现产物 v1 后，运行状态为「已完成」。评审账号直接请求两个 agent 的原始私聊，均返回 HTTP 403。
